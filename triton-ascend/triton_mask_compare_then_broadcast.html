Compare-then-Broadcast

Why k_attn_arg[None, :] == 0 lowers to a [1,128] compare followed by a broadcast, and not a broadcast followed by a [64,128] compare — a trace of Triton’s frontend lowering.

Source of the IR: GitHub issue rainbay001-dotcom/test#1 — the tt.-dialect TTIR dump of @fwd_kernel from flash_attention_npu_v9_mask_in.py, target Ascend950PR_9579. Source of the Python: ~/Documents/docs/helloworld.py (the standalone 1:1 extraction of that kernel’s mask_fn, TYPE==1). Compiler internals verified against the local fork Triton-Ascend/python/triton/language/semantic.py (triton-ascend 3.2.0). Compiled 2026-05-31.

1. The two lines in question

Inside the mask region of the issue’s TTIR, two adjacent operations:

%84 = arith.cmpi eq, %81, %cst : tensor<1x128xi32>     // C := (k_attn == 0), compared at [1,128]
%85 = tt.broadcast %84 : tensor<1x128xi1> -> tensor<64x128xi1>   // then broadcast the i1 result to [64,128]

The natural expectation would be the opposite order — broadcast k_attn to [64,128] first, then do a full 64×128 compare. This page explains why the compiler does it the way it does, and shows that the answer is structural, not a cost heuristic.

The one-sentence answer. The broadcast is not part of == 0 at all. The == sub-expression only ever produces [1,128] (its operands are a [1,128] vector and a scalar). The [64,128] broadcast belongs to the enclosing | operator, applied to the already-finished [1,128] result. They are two different operators at two different levels of the expression tree, emitted at two different times.

2. The source expression

From helloworld.py, the TYPE==1 branch of mask_fn (the highlighted line is C):

@triton.jit
def mask_fn(q_attn_arg, k_attn_arg, q_offset, k_offset, TYPE: tl.constexpr):
    if TYPE == 1:
        triu_causal = (q_offset[:, None] <= k_offset[None, :])        # A  →  [64,128]
        return(
            (triu_causal &
            ((q_attn_arg[:, None] == k_attn_arg[None, :]) |          # B  →  [64,128]
            (k_attn_arg[None, :] == 0))) |                          # C  →  [1,128]   ← these two IR lines
            (q_offset[:, None] == k_offset[None, :]))                # D  →  [64,128]

The whole mask is the boolean tree (A & (B | C)) | D. Three of the four leaves (A, B, D) carry a [:, None] row term, so they are inherently [64,128]. Only C is purely [None, :] column-indexed and compared against a scalar — that is the entire reason it behaves differently.

3. The killer contrast — same input, two orderings, visible in the IR

Both B and C compare against k_attn[None,:], which is the single SSA value %81 (tt.expand_dims of the loaded tensor<128xi32> key vector). Watch what each does with it:

// %81 = k_attn[None, :]  :  tensor<1x128xi32>     (shared by B and C)

// ---- B : broadcast → then compare ----
%82 = tt.broadcast %81 : tensor<1x128xi32> -> tensor<64x128xi32>   // k_attn widened to [64,128] FIRST
%83 = arith.cmpi eq, %66, %82 : tensor<64x128xi32>          // compare at [64,128]   (%66 = q_attn[:,None])

// ---- C : compare → then broadcast ----
%84 = arith.cmpi eq, %81, %cst : tensor<1x128xi32>           // compare at [1,128] FIRST   (%cst = dense<0>)
%85 = tt.broadcast %84 : tensor<1x128xi1> -> tensor<64x128xi1>    // broadcast the i1 RESULT to [64,128]

Same %81. B broadcasts the input up to [64,128] and then compares; C compares at [1,128] and then broadcasts the output. The difference is decided entirely by the other operand of each ==:

  • B’s other operand is %66 = q_attn[:, None], a [64,128] block → the compare is forced to [64,128].
  • C’s other operand is the literal 0, a scalar → it splats to %81’s shape [1,128], so the compare stays [1,128]. The 64 is nowhere in C’s operands.

4. The expression tree — where each op lives

Triton’s frontend walks the Python operator-precedence tree bottom-up, emitting MLIR eagerly at each node. The == of C is a child; the | that broadcasts it is its parent. The child is fully evaluated (and its [1,128] compare emitted) before the parent ever runs — so the parent can only broadcast the result it was handed.

■ C is compared at [1,128] (green)  ·  ■ the broadcast (orange) is injected by C’s parent |, on the path up from C  ·  ■ A/B/D are already [64,128]

The same tree as ASCII, for reference:

                | (or_, %89)                 (A&(B|C)) | D        [64,128]
               / \
   (and_,%87) &   cmpi eq %88  = D            q_off == k_off       [64,128]
             / \
  (sle,%80) A   | (or_, %86)   = B|C   ◀── broadcast injected here  [64,128]
               / \
   (eq,%83) B    ╎
                 ▼ tt.broadcast %85          [1,128] → [64,128]   ◀── the broadcast
                 ╎
                 cmpi eq %84  = C            k_attn[None,:] == 0   [1,128]  ◀── the compare

5. Which part of the compiler emits this

These are tt.-dialect (TTIR) operations, so they are produced by stage ① — the Triton Python frontend, the AST→TTIR builder. This is above the GPU/Ascend fork point: neither triton-adapter-opt nor bishengir creates this pattern; they only consume/lower it later. It is also stock upstream Triton (NumPy-style implicit broadcasting), not anything triton-ascend added — the same IR is generated on the CUDA path.

@triton.jit (.py)
      │  ① Triton frontend  ← these two lines are born HERE
      ▼
   TTIR (tt.*)          ── %84 cmpi eq [1,128] , %85 tt.broadcast →[64,128]
      │
      ├─[NVIDIA/AMD] → TTGIR (ttg.*) → LLVM → PTX
      └─[Ascend]     → ttadapter (triton-adapter-opt) → HFusion/HIVM (bishengir) → elf64-hiipu

7. Why compare-then-broadcast, and not broadcast-then-compare

Three facts combine:

  1. Eager, bottom-up IR construction. Every tl operator immediately calls builder.create_* and returns a concrete typed tl.tensor. There is no global shape inference — each operator rank-matches only its own two operands.
  2. == 0 has no 64 in its operands. Its operands are k_attn[None,:] ([1,128]) and the scalar 0. The scalar splats to [1,128]; the compare is emitted at [1,128]. Nothing here could widen it to 64 rows.
  3. The 64 lives one level up, in a sibling. It enters only when the parent | rank-matches its [64,128] operand B against C’s [1,128]. By then C is already a finished [1,128] value (%84); the only thing the | can do is broadcast that result.

For the order to be reversed (broadcast-then-compare), k_attn would have to reach [64,128] before the == ran — which requires the == to know its result needs 64 rows. It cannot: the parent’s shape requirement cannot flow back down into a child the frontend has already emitted. A child node is sealed the moment it returns its tl.tensor.

The general rule. A broadcast is emitted at the operator whose two operands have mismatched shapes, on whichever operand is smaller (broadcast_impl_value, semantic.py:829–844: the result takes the non-1 dimension on each axis; only an operand differing from the result is broadcast).
  • B’s ==: operands [64,1] vs [1,128] → the mismatch is intrinsic to the compare → broadcast → compare.
  • C’s ==: operands [1,128] vs scalar → no row mismatch → compare at [1,128]; the 64 appears only at the parent | → compare → broadcast.
It is a purely local, syntactic consequence of where the differing-shape operand sits in the tree — not a cost decision, not a global optimization.

8. Why the local rule happens to be the efficient one

Comparing 128 lanes once and broadcasting a 1-bit-per-lane predicate to 64 rows is much cheaper than broadcasting the i32 input to [64,128] and doing a full 64×128 compare. Because the source kept the row-independent term (k_attn==0) as its own sub-expression, Triton’s eager bottom-up broadcasting produces exactly the cmpi[1,128] → broadcast[64,128] shape that bishengir later lowers into the special precompute-once C-path (the VDUPS / VLDAS→VLDUI→MOVVP recovery measured in assembler.as). The efficiency is, at root, an emergent property of how this one sub-expression was written plus Triton’s local broadcast rule — decided in the frontend, before any Ascend pass sees it.

Equivalently: A/B/D each mix a [:,None] row term with a [None,:] column term, so their comparisons are inherently [64,128] and use all 64 rows of real work. C depends only on the key/column index, so it is identical down all 64 rows — the compiler computes it once on one row and replicates the bits. That asymmetry is the seed of the “special handling of C” seen all the way down at the assembler level.
